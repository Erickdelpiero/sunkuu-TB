# B-01 — Guion de pruebas técnicas (Opción B)

Fecha: 2026-10-19 · Diseño: `docs/arquitectura/2026-10-19-diseno-B.md` (§2.1, §3.3, §7) · Base: `../sunkuu-tb-config` `0c3d0ff`.
Ejecuta: Erick, con su admin del tenant (usuario GONEX) y con el usuario de "GONEX QA (prueba)". Tiempo estimado: 1–1,5 h.

**Qué decide cada prueba**

| # | Prueba | Decide |
|---|---|---|
| 1 | Consulta Q1 tal cual, con el usuario QA y con el admin | El cuerpo exacto de Q1 (`SERVER_ATTRIBUTE` o `ATTRIBUTE`, atributo JSON, orden) |
| 2 | Propietario: campo `ownerName` (Q2a) o grupo "All" (Q2b) | Cómo resuelven el propietario Flota, Exportación y el NAV para el admin |
| 3 | El usuario QA lee su propio customer | De dónde sale el nombre del customer en Flota para el cliente |
| 4 | El usuario QA carga un recurso JS del tenant | P-1: catálogo y módulo común en un recurso JS o como constante por widget |
| 5 | Endpoints del formulario (admin), con una escritura en QA | Las rutas del formulario "Registrar instalación" |
| 6 | Usuario QA sin grupo | Que el módulo trate como *fail-closed* tanto una lista vacía como un 403 |

**Reglas**
- Todo se hace sobre entidades de QA. La única escritura en producción es la creación del recurso de prueba (prueba 4). En la prueba 5 se crea `QA-Instalación-2`, que se reutiliza en B-04: ocupa 1 de los 100 activos de la licencia.
- No pegues tokens, contraseñas ni correos en los resultados.
- Cada comando es de una línea (un bloque de código = un comando). Requisitos: `curl` y `jq` (`sudo apt install jq`).
- Si un comando devuelve un error de JSON (`parse error`), vuelve a ejecutarlo sin el `| jq …` final para ver la respuesta cruda (normalmente un `401` por token vencido: repite el login).

## Prueba 4 — Recurso JS del tenant leído por el usuario QA

**4.0 Crear el recurso de prueba en la UI (admin GONEX).**
1. En tu equipo, crea el archivo `sunkuu-b01-prueba.js` con este contenido (una línea de comentario y una de datos):
   ```
   /* Sunkuu 360 · B-01 · recurso de prueba (se reemplaza en B-02) */
   var SUNKUU_B01 = { ok: true, prueba: "B-01", fecha: "2026-10-19" };
   ```
2. Menú lateral **Recursos → Biblioteca JavaScript** (en algunas versiones aparece como "Biblioteca de recursos": en ese caso elige el tipo "Módulo JS").
3. Botón **+** → **Agregar recurso JavaScript**. Subtipo: **Módulo** si te lo pregunta. Título: `sunkuu-b01-prueba`. Arrastra el archivo. **Agregar**.
4. No marques ninguna opción de sistema ni de "público". Es un recurso del tenant, igual que lo sería el módulo real.
5. Al guardar se genera un auto-commit o no; en todo caso se cubre con la versión manual del cierre.

**4.1**
```
curl -s "$H/api/resource?pageSize=50&page=0&textSearch=sunkuu-b01" -H "X-Authorization: Bearer $TA" | jq "[.data[] | {title, resourceType, resourceKey, id: .id.id, link}]"
```
- Esperado: Una fila: `resourceType` `JS_MODULE`, `resourceKey` `sunkuu-b01-prueba.js` y un `link` del estilo `/api/resource/js_module/tenant/sunkuu-b01-prueba.js`
- Interpretación: Anota `link` e `id`. Si no hay `link`, usa la forma del ejemplo

**4.2**
```
RL=$(curl -s "$H/api/resource?pageSize=50&page=0&textSearch=sunkuu-b01" -H "X-Authorization: Bearer $TA" | jq -r '.data[0].link // empty'); echo "$RL"
```
- Esperado: La ruta del recurso
- Interpretación: Si sale vacío: `RL=/api/resource/js_module/tenant/sunkuu-b01-prueba.js`

**4.3**
```
curl -s -w '\nHTTP %{http_code}\n' "$H$RL" -H "X-Authorization: Bearer $TA"
```
- Esperado: El contenido del archivo y `HTTP 200`
- Interpretación: Control: el admin lo descarga

**4.4**
```
curl -s -w '\nHTTP %{http_code}\n' "$H$RL" -H "X-Authorization: Bearer $TQ"
```
- Esperado: **El contenido y `HTTP 200`**
- Interpretación: ✔ `200` → **P-1 = recurso JS** (catálogo + módulo común). `403` → **constante por widget**. `404` con el admin en `200` → anotarlo: puede ser otra ruta para clientes, se revisa antes de decidir

**4.5**
```
curl -s -w '\nHTTP %{http_code}\n' "$H/api/resource/$(curl -s "$H/api/resource?pageSize=50&page=0&textSearch=sunkuu-b01" -H "X-Authorization: Bearer $TA" | jq -r '.data[0].id.id')/download" -H "X-Authorization: Bearer $TQ"
```
- Esperado: `200` o `403`
- Interpretación: Solo informativo: la ruta que usan los widgets es la de 4.4


La confirmación final (el recurso declarado en "Resources" de un widget, abierto por el usuario QA en el navegador) se hace en B-04 con las copias DEV.
