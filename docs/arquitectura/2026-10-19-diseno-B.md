## 1. Esquema del activo "Instalación"

### 1.1 Entidad

| Campo | Valor |
|---|---|
| Perfil | "Instalación" (`a1683c90`). Los widgets lo buscan **por nombre** (`assetTypes:["Instalación"]`), sin UUID en el código |
| Propietario | El customer. Se crea dentro del grupo "All" de activos del customer, o se pasa con "Cambiar propietario". Un activo del tenant (como `QA-Ajeno`) **no es una instalación válida** y ningún widget lo muestra |
| `name` | Único en el tenant. Convención (P-8): `INST · <etiqueta>`, p. ej. `INST · TG Gocta`. Se puede renombrar sin efectos: ninguna integración busca activos por nombre |
| `label` | Igual a `etiqueta`, para que se lea bien en la UI nativa (los widgets usan el atributo) |
| Licencia | 1 activo por instalación, de 100 (hoy hay 3, todos de QA: `QA-Instalación-1`, `QA-Instalación-2`, `QA-Ajeno` [B-01]) |

### 1.2 Atributos (todos `SERVER_SCOPE`)

El cliente los lee (rol con `READ_ATTRIBUTES` sobre lo suyo) y no los puede escribir (sin `WRITE_ATTRIBUTES`). Solo el tenant edita.

| Atributo | Tipo TB | Obligatorio | Contenido | Si falta o es inválido |
|---|---|---|---|---|
| `tipo` | string | sí | Clave del catálogo de tipos (§1.3): `3em`, `piscina`, `proem` | La instalación se ignora (aviso en consola) |
| `dashboard_id` | string | sí | UUID del dashboard de la instalación | Se ignora |
| `dispositivos` | JSON | sí | Objeto rol → UUID, con los roles del tipo. `3em`/`proem`: `{"principal":"…"}`. `piscina`: `{"cal":"…","ilu":"…","amb":"…"}` (mismas claves que el CFG actual de Piscina) | Se ignora si falta un rol obligatorio del tipo |
| `etiqueta` | string | sí | Nombre visible en los 4 widgets | Se usa `label` y, si tampoco hay, `name` |
| `ubicacion` | string | no | "Distrito, Región" de la instalación | Vacío |
| `orden` | long | no | Orden global en las listas (10, 20, 30…) | Al final, por etiqueta |
| `es_prueba` | boolean | sí (el formulario siempre lo escribe) | `true` = fuera de la Capa 0, de los KPI de Flota y del conteo de clientes | **Se trata como `true`** (*fail-closed* sobre los KPI) |
| `mostrar_parametros` | boolean | no | `true` = el cliente ve en 3EM/Piscina el panel de parámetros **en solo lectura**. El formulario de edición sigue siendo solo del tenant. Se implementa en FIX-02 (P-9) | `false` (defecto): el cliente no ve el panel |
| `activa` | boolean | no (el formulario siempre lo escribe) | `false` = baja sin eliminar: la instalación desaparece de las listas, del NAV y de los KPI, y conserva activo, dispositivos, telemetría y dashboard (P-15) | `true` (defecto) |

No se duplican en el activo: la tarifa (`tarifa_kwh` del dispositivo), los umbrales ni el nombre del customer (sale del propietario).

## 2. Cómo obtiene cada widget lo que hoy sale de sus arrays

### 2.1 Módulo común `loadInstallations(ctx, cb)`

Firma fijada en B-02: recibe el `ctx` del widget (necesita `ctx.http`). Implementación y pruebas: `docs/qa/2026-10-21-B-02.md`.

Mismo código en los 4 widgets, alojado en el recurso JS de §1.3. Siempre con `ctx.http` (encamina F23 e I-04) y siempre *fail-closed*: un error o una respuesta vacía produce lista vacía y el mensaje "No hay instalaciones asignadas", nunca la lista completa.

**Consulta Q1: instalaciones visibles para el usuario.**
```json
POST /api/entitiesQuery/find
{
  "entityFilter": { "type": "assetType", "assetTypes": ["Instalación"] },
  "entityFields": [ { "type": "ENTITY_FIELD", "key": "name" }, { "type": "ENTITY_FIELD", "key": "label" },
                    { "type": "ENTITY_FIELD", "key": "ownerName" }, { "type": "ENTITY_FIELD", "key": "ownerType" } ],
  "latestValues": [
    { "type": "SERVER_ATTRIBUTE", "key": "tipo" },        { "type": "SERVER_ATTRIBUTE", "key": "dashboard_id" },
    { "type": "SERVER_ATTRIBUTE", "key": "dispositivos" }, { "type": "SERVER_ATTRIBUTE", "key": "etiqueta" },
    { "type": "SERVER_ATTRIBUTE", "key": "ubicacion" },    { "type": "SERVER_ATTRIBUTE", "key": "orden" },
    { "type": "SERVER_ATTRIBUTE", "key": "es_prueba" },    { "type": "SERVER_ATTRIBUTE", "key": "mostrar_parametros" },
    { "type": "SERVER_ATTRIBUTE", "key": "activa" }
  ],
  "pageLink": { "page": 0, "pageSize": 200, "sortOrder": { "key": { "type": "SERVER_ATTRIBUTE", "key": "orden" }, "direction": "ASC" } }
}
```
- **Usuario de customer:** devuelve solo los activos de su customer [B-00, B-01]. Es la única consulta que necesita.
- **Tenant:** devuelve todos (QA y los del tenant incluidos), cada uno con su propietario (Q2a).
- **`SERVER_ATTRIBUTE`** [B-01: funciona igual que `ATTRIBUTE`; se usa el más estricto].
- **Los valores llegan como texto** [B-01]: `"900"`, `"true"`, el JSON de `dispositivos` como texto. El módulo convierte `orden` a número, `activa` y `es_prueba` a booleano (`"true"`/`"false"`) y `dispositivos` con `JSON.parse`; si el parse falla, descarta la instalación.
- **Orden en el cliente** [B-01]: con `ASC`, los activos sin `orden` salen primero. El módulo reordena: por `orden` numérico y los que no tienen `orden` al final (por etiqueta). El `sortOrder` de la consulta queda solo como orden inicial.
- Validación en el cliente: se descarta (con aviso en consola) toda instalación con `ownerType` ≠ `CUSTOMER`, sin `tipo` del catálogo, sin `dashboard_id` o con `dispositivos` que no sea JSON válido o al que le falte un rol obligatorio. Las de `activa=false` se descartan sin aviso. El resto se muestra.
- Respuesta vacía (`totalElements: 0`, HTTP 200) o error (incluido 403): lista vacía con el mensaje. Un usuario sin grupo inicia sesión y recibe 0 [B-01].

**Propietario: Q2a (decidido con B-01).** `ownerName`/`ownerType` vienen en la misma Q1 [B-01]: para el admin, `QA-Ajeno` → TENANT "Sunkuu Energy S.A.C." y `QA-Instalación-1` → CUSTOMER "GONEX QA (prueba)". El usuario QA también recibe `ownerName`. **Una sola llamada** para todos los widgets. Se descarta todo activo con `ownerType` ≠ `CUSTOMER`. La agrupación por customer usa `ownerName` (el título del customer es único en el tenant).

**Respaldo: Q2b** (no se usa salvo que Q2a deje de funcionar; sus rutas no se informaron en los resultados de B-01):
- **Q2b (por grupo).** `POST /api/entitiesQuery/find` con `entityFilter: {"type":"entityType","entityType":"CUSTOMER"}` (campos `title`, `city`, `state`, `country`, `email`). Para cada customer, `GET /api/entityGroups/CUSTOMER/{customerId}/ASSET`, tomar el grupo "All" y repetir Q1 con `entityFilter: {"type":"entityGroup","groupType":"ASSET","entityGroup":"<id>"}` y un `keyFilter` ENTITY_FIELD `type` = "Instalación". Con 5 customers son 11 llamadas.
  - Aplica por construcción la regla "propiedad del customer": un activo del tenant (`QA-Ajeno`) nunca aparece.

**¿Relación o grupo?**
- **Propietario y visibilidad:** grupo/propietario, no relación. Es lo que filtra el rol del cliente [B-00].
- **Dispositivos:** atributo JSON (decidido). Una relación `Contains` Instalación → Dispositivo no se necesita en B. Podría servir más adelante para propagar alarmas al activo y contar las de Flota con una sola consulta (pregunta P-14, fuera de B).
- **Dashboards:** no hay que listarlos. El usuario de customer no puede listar los dashboards del tenant, pero no lo necesita: `dashboard_id` viene en el activo, y la compartición sigue siendo por grupo de dashboards.

**Capa 0 de Flota (admin).**
- Filas = customers con al menos una instalación `es_prueba=false`, en orden alfabético; dentro de cada uno, por `orden`.
- Los customers de prueba (solo instalaciones `es_prueba=true`, como GONEX QA) no aparecen.
- KPI y "Requieren acción": solo instalaciones `es_prueba=false`.
- "Clientes activos *X* de *N*": X = customers con alguna instalación con datos recientes; N = customers con al menos una instalación activa no de prueba (P-6). Un customer sin instalaciones (Apu Samay hoy) no cuenta en N ni aparece en la Capa 0.
- "de 4 instalaciones monitoreadas" = cantidad de instalaciones no de prueba, calculada.
- Con esto se cierran A3-3, A3-5 y F07 (resto) sin necesidad de R0.

### 2.3 NAV de 3EM y Piscina (regla de negocio)

1. `curD` = UUID del dashboard actual (como hoy, desde la URL).
2. Instalación actual = la de Q1 con `dashboard_id` = `curD`.
   - Tenant y cliente: la misma Q1 (con `ownerName`); sin llamadas extra.
3. Opciones = las instalaciones **del mismo propietario** que la actual, menos la actual, ordenadas por `orden`. Las de prueba solo aparecen si la actual también es de prueba.
4. **Si el dashboard actual no está en el registro** (dashboard nuevo sin registrar, copia DEV): sin desplegable (se oculta el caret, como hoy cuando no hay opciones).

Efecto para el admin: deja de ver mezclados los dashboards de todos los customers (P-12 del triage / R0b); ve los del customer del dashboard que tiene abierto. Para ir a otro customer usa Flota.

Los puntos de color del desplegable (3EM los pinta con la frescura del dispositivo **actual**; Piscina los deja vacíos) se retiran: mostrar una frescura que no corresponde es peor que no mostrarla. El estado por instalación queda para Flota.

## 3. Formulario "Registrar instalación"

### 3.1 Dónde vive

- Widget nuevo "Sunkuu — Registro de instalaciones" en un **dashboard nuevo "Administración — Sunkuu 360"**, propiedad del tenant y **sin compartir con ningún grupo de customer**.
- El widget además comprueba `authority === 'TENANT_ADMIN'` y, si no lo es, no muestra nada.
- Acceso: botón "Administración" en el encabezado de Flota, visible solo para el tenant. Esto vale también como E.1 para Romel.
- Decidido (P-5): dashboard propio, no dentro de Flota.

### 3.2 Campos y listas

| Campo | Control | Origen de la lista |
|---|---|---|
| Customer | lista | `entitiesQuery` CUSTOMER (`title`). Los de nombre con "Prueba", "Gonex" o "Erick" (regla de `CLAUDE.md`) se marcan "(prueba)" y proponen `es_prueba=true` |
| Tipo | lista | Catálogo de tipos (§1.3) |
| Dispositivo por rol | una lista por rol del tipo | `entitiesQuery` DEVICE con `entityFilter: {"type":"deviceType","deviceTypes":[<perfil del rol>]}` (campos `name`, `label`), **menos los ya referenciados** en algún `dispositivos` del registro. Cada opción muestra el propietario actual. Los roles opcionales admiten "ninguno" |
| Dashboard | lista | `GET /api/tenant/dashboards?pageSize=100&page=0` (`title`), menos los ya referenciados en `dashboard_id`, Flota y Exportación |
| Etiqueta | texto | Propuesta: título del dashboard elegido |
| Ubicación | texto | Propuesta: `city`, `state` del customer |
| Orden | número | Propuesta: último `orden` + 10 |
| Es de prueba | casilla | Propuesta según el nombre del customer |
| Mostrar parámetros al cliente | casilla | `false` por defecto (P-9) |
| Activa | casilla | `true` por defecto (P-15) |

Modo edición: el mismo formulario abre una instalación existente y permite cambiar todo **menos el propietario**. El cambio de propietario es un traslado (§4). La baja es `activa=false`. Nunca elimina.

### 3.3 Validaciones (bloquean el guardado salvo las marcadas como aviso)

1. Campos obligatorios completos; `orden` entero; el `tipo` existe en el catálogo.
2. **Dispositivos:** existen, su perfil coincide con el del rol, el `name` cumple el prefijo del tipo (si lo tiene) y no están en otra instalación.
3. **Propietario del dispositivo = customer elegido.** Si no coincide, bloquea y explica que hay que hacer "Cambiar propietario" desde la UI (nunca eliminar). El formulario no cambia propietarios (P-3).
4. **Dashboard:** existe y no está en otra instalación.
5. **Compartición del dashboard** con el customer:
   - Grupo "Customer Users" del customer: `GET /api/entityGroups/CUSTOMER/{customerId}/USER`.
   - Sus permisos: `GET /api/userGroup/{groupId}/groupPermissions`. Grupos de dashboards compartidos: los permisos con `entityGroupType` DASHBOARD.
   - Comprobar que alguno contiene el dashboard: `GET /api/entityGroup/{dashboardGroupId}/entities?pageSize=100&page=0`. Devuelve los ids con `name` nulo [B-01]: los títulos se obtienen cruzando con `GET /api/tenant/dashboards`.
   - Si no lo contiene: **aviso** "El customer no verá este dashboard: agréguelo a su grupo de dashboards" (paso 4 del alta, manual hasta C).
   - Si el dashboard está en un grupo compartido con **otro** customer: **bloquea** (fuga entre clientes).
6. **Grupo "Customer Users":**
   - Debe existir y tener el rol genérico de cliente: si no, bloquea.
   - Usuarios del customer (`GET /api/customer/{customerId}/users?pageSize=100&page=0`) frente a los miembros de "Customer Users" y "Customer Administrators". Cada usuario que no esté en ninguno genera el **aviso** "<usuario> no está en el grupo Customer Users: no verá ninguna instalación" (el caso de Apu Samay hoy).
   - Un customer sin usuarios genera un aviso.
   - El formulario **no crea usuarios** (es C) ni los agrega al grupo: solo avisa (P-4).
7. **Licencia:** total de activos (`GET /api/tenant/assets?pageSize=1&page=0` → `totalElements`) < 100; si quedan menos de 10 libres, aviso.
8. **Nombre único:** `GET /api/tenant/assets?assetName=<name>`. Si ya existe con el mismo propietario, se ofrece "actualizar" (idempotencia); si existe con otro propietario, bloquea.

Rutas confirmadas en B-01: `entityGroups/CUSTOMER/{id}/USER`, `userGroup/{id}/groupPermissions` (Gocta: "Customer User" + "Entity Group Read-only User" sobre DASHBOARD "Gocta Andes Lodge"; QA: solo "Customer User"), `customer/{id}/users`, `entityGroup/{id}/entities`, `tenant/assets` y `tenant/devices` (conteo), `tenant/assets?assetName=`, `assetProfileInfos`, `tenant/dashboards` y el filtro `deviceTypes`.

### 3.4 Qué escribe y en qué orden

1. **Activo.** `POST /api/asset?entityGroupId=<grupo "All" de activos del customer>` con `{name, label, type:"Instalación", assetProfileId}`. Queda como propiedad del customer sin otro paso [B-01: `QA-Instalación-2` `71b95240`]. El id del perfil se obtiene por nombre, sin escribirlo en el código. Si el activo ya existe (8), se reutiliza.
2. **Atributos.** Una sola llamada `POST /api/plugins/telemetry/ASSET/{id}/attributes/SERVER_SCOPE` con los 9 atributos. `dispositivos` se envía como objeto, para que quede como atributo JSON.
3. **Relectura.** Q1 con `keyFilter` `dashboard_id` = el elegido. Se compara con lo escrito y se muestra la **vista previa**: "Así lo verá cada widget" (fila en Flota, tarjeta en Exportación y NAV del customer).

   - Si hubo avisos de compartición o de grupo, resolverlos.

Si el paso 2 falla, el activo queda sin atributos y **ningún widget lo muestra** (Q1 descarta la instalación incompleta). El formulario lo detecta por nombre y ofrece "Completar". Nunca se borra nada.
